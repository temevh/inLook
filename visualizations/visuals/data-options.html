Inlook · Data options

Person 2 turns input (mic, selection, screenshot) into claims. Person 3 checks the claims: match, source re-check, verdict, tier routing, storage, reviews. They connect through one function, check_claim.

1. check_claim input

A. Standalone claim, check_claim owns the lifecycle Recommended

check_claim({ text, quote, source: "audio"|"selection"|"screenshot", speaker?, lineId? })

text is rewritten by Gemini spot to stand alone ("Competitor X charges €59 per seat"); quote is the raw words. check_claim makes the claimId, publishes claim.spotted, then checks.

  • Pros: the claimId is made in one place; person 3 owns everything from "Checking…" to the verdict; person 2's interface is one call.
  • Cons: spot must rewrite claims well ("they charge €59" needs the earlier lines).

B. Person 2 publishes claim.spotted first

publish("claim.spotted", { claimId, … })
check_claim({ claimId, text, source })

Person 2 publishes claim.spotted with a claimId, then calls check_claim({ claimId, text, source }).

  • Pros: the HUD shows "Checking…" even before person 3's code exists.
  • Cons: two owners for one claim's lifecycle; claimIds made in two places.

C. Raw text, person 3 finds the claims too

check_text({ text, source, lines? })

Person 3 runs spot and check in one Gemini call.

  • Pros: possibly one Gemini call instead of two.
  • Cons: person 2 has almost nothing left to own; one function does two jobs; screenshots don't fit.

2. How check_claim is called

A. Fire and forget Recommended

check_claim starts a background task and returns at once.

  • Pros: transcription never waits; checks run in parallel.
  • Cons: verdicts can arrive out of order (fine, because cards are keyed by claimId).

B. Await, one at a time

  • Pros: simplest; strict order.
  • Cons: a 3–10 s check holds up every claim behind it.

C. Queue + 1 worker

  • Pros: ordered, and doesn't block input.
  • Cons: the wait grows when many claims come in; more code.

3. Repeated claims

A. check_claim skips a fact already checked in the last N minutes Recommended

  • Pros: catches the same fact even when it's worded differently.
  • Cons: the match call still runs on every repeat.

B. spot drops claims whose text matches a recent one

  • Pros: no Gemini call for repeats.
  • Cons: misses rewordings.

C. No dedup

  • Pros: no code.
  • Cons: noisy HUD, extra Gemini cost.

4. Fact shape

A. Flat fact, value as text, versions embedded Recommended

{ id, key, label, value: "€59 per seat", tier: "low"|"medium"|"high", sourceUrl, statedBy,
  status: "current"|"outdated"|"pending_review", versions: [{ value, source, at, by }] }
  • Pros: matches the existing FactVersion and the card line "€59 → €39"; one read per fact; Gemini compares text well.
  • Cons: no number comparisons or thresholds.

B. Typed value

value: { amount: 59, unit: "EUR/seat" }   // or a type tag per fact
  • Pros: exact comparisons; can be charted.
  • Cons: every kind of fact (names, dates, wifi names) needs its own shape; Gemini must output exact numbers.

C. Versions in their own collection

facts    { id, currentVersionId, … }
versions { id, factId, value, source, at, by }
  • Pros: easy history queries and an audit trail.
  • Cons: two writes per update and joins; too much for a demo.

5. Where the data lives (demo)

A. JSON seed file loaded into memory Recommended

backend/seed.json   // facts, strategies, people · loaded at start
  • Pros: no setup; restarting resets it for every demo take; easy to review in git.
  • Cons: changes are lost on restart; one process only.

B. SQLite

  • Pros: persists in one file; real queries.
  • Cons: schema and migration code.

C. MongoDB Atlas (the spec's original plan, unconfirmed)

  • Pros: change streams; matches the spec.
  • Cons: needs an account and a network connection during the demo; most code.

6. Other records

Keep the spec's shapes Recommended

strategies { id, name, owners: [personId], factIds: [factId], status: "healthy"|"flagged" }
people     { id, name, role, team }
reviews    { id, factId, oldValue, newValue, evidence, tier, reviewers: [personId], status: "pending"|"accepted"|"rejected" }
messages   { id, to: [personId], strategyId, factId, text, at }

7. Tier

A. Stored per fact, floor applied at load Recommended

Any fact a strategy uses is raised to at least medium when the seed loads.

  • Pros: one place for the rule; tier is just a field at check time.
  • Cons: changing a strategy's facts means reloading.

B. Computed at every check

  • Pros: always current.
  • Cons: the rule runs in the hot path; easy to forget in one place.

8. IDs

A. Readable slugs Recommended

f-compx-price   s-pricing   p-ada
  • Pros: already used by the mock fixtures; readable in logs and the HUD.
  • Cons: must be unique by hand.

B. UUIDs

  • Pros: never collide.
  • Cons: unreadable; the fixtures need changing.

C. Mongo ObjectIds

  • Pros: native if Mongo is chosen.
  • Cons: ties the IDs to the storage choice.
